# 개발 기록

형식: 측정 → 가설 → 수정 → 재측정. 숫자는 이 PC(Windows 11, Edge 156) 기준.
좋아지지 않은 시도도 지우지 않고 남긴다.

## 0. 시작 (2026-11-04)
- 스택: Vite 8.3 / React 19.3 / TypeScript 7.0 / Vitest 5.1 / Node 24
- 빈 앱 빌드: JS 219 kB (gzip 68.6 kB). 거의 전부 React다. 이후 첫 화면 예산의 기준점.
- 공용 스키마 테스트 7개 통과(라벨 허용 목록, 숫자 범위, 모르는 필드 버림, 배치 크기, 메시지 정화).

## 1. Worker 풀
- 가짜 워커로 테스트 8개(동시 실행 제한, 순서, 대기/실행 중 취소, 시간 초과, 충돌 복구, 늦은 메시지 무시).
- **첫 실행에서 6개 실패.** 전부 즉시 '시간 초과'.
  - 원인: `{ 기본값, ...opts }` 합치기에서 호출부가 `defaultTimeoutMs: undefined`를 넘기면 기본값이 덮이고 `setTimeout(fn, undefined)` = 0ms.
  - 수정: `opts.defaultTimeoutMs ?? 기본값`. 실제 앱에서도 터졌을 버그.

## 2. SSIM (스마트 압축의 화질 기준)
### 정확도: 남이 만든 구현과 대조
- 기준판(Wang 2004, 11×11 가우시안 σ=1.5)을 scikit-image 0.26 값과 비교. 합성 이미지 1장 + 변형 7종(JPEG 95/80/60/30/10, 흐림, 노이즈).
- 1차: 6종 일치, **흐림만 0.0032 차이**(허용 0.003 초과).
  - 가설: 계산식이 아니라 테두리 처리 차이(나는 끝 값 반복으로 전체 평균, skimage는 반지름 5 테두리 제외).
  - 검증: 테두리 제외로 바꾸자 7종 전부 차이 ≤ 0.000002. 가설 맞음. 허용치를 0.00001로 조임.

### 속도·메모리 (4000×3000, Node 24)
측정 횟수: 기준판은 4번(1385\~1409 ms), v2는 1번, v3와 대칭판은 번갈아 5번씩 돌린 중앙값.
| 버전 | 시간 | 추가 메모리 | 변경 |
|---|---|---|---|
| 기준판 | 1397 ms | 약 620 MB(13개 배열) | 논문 그대로 |
| v2 | 805 ms | 240 MB | 안쪽만 계산, 곱 배열 제거, 세로 결과 저장 안 함 |
| v3 | **512 ms** | **약 1 MB** | 가로 블러를 11줄 고리 버퍼에만 보관 |
| v3+대칭 커널 | 502 ms(가끔 610) | 약 1 MB | 곱셈 절반. **차이 2%로 잡음 수준 → 되돌림** |
- v3는 기준판과 값이 1e-6 안에서 같음(테스트로 고정).
- 배운 것: 처음 속도 개선(1.7배)보다 메모리 구조를 바꾼 쪽(추가 1.6배)이 더 컸다. 곱셈 수 줄이기는 JS 엔진이 이미 해 주는 수준이라 의미 없었다.
- 남은 선택지: WASM SIMD, 축소 후 비교. 스마트 압축에서 실제 병목인지 확인한 뒤 결정.

## 3. 스마트 압축: 품질 탐색 알고리즘
### 실험 방법
- 데이터: Kodak 이미지(압축 연구 표준 세트) 24장 중 22장(01·23번은 3회 재시도에도 다운로드 실패).
- 정답표: 사진 22장 × JPG(mozjpeg)/WebP/AVIF(speed 6) × 품질 1\~100 **전부** 인코딩 → [품질, 바이트, SSIM]. 6,600회.
  - 평균 비용(768×512): JPG 인코딩 약 55ms, WebP 46ms, **AVIF 309ms**, 디코딩+SSIM 23\~43ms.
- 최적값 = 목표 SSIM 이상 중 가장 작은 파일. 탐색이 고른 결과와 비교해 **손해(용량 차이)**·**놓침**·**인코딩 횟수**를 잰다.
- 예측값을 쓰는 전략은 **leave-one-out**(시험할 사진은 학습에서 뺌)으로만 평가해 과적합을 막았다.
- 곡선 성질: q가 1 오를 때 SSIM이 떨어지는 비율 JPG 0.2% / WebP 3.2% / AVIF 0%.

### 버전별 결과(목표 0.95\~0.99 평균 인코딩 횟수, 손해는 전부 0%. 단 WebP 0.95는 모든 전략이 평균 0.21%)
| 버전 | 방법 | JPG | WebP | AVIF |
|---|---|---|---|---|
| v1 | 정수 이분 탐색 | 7.7 | 7.6\~8.0 | 7.7\~7.8 |
| v2 | 보간(SSIM 그대로 / -log(1-SSIM)) | 5.0\~8.0 | 5.3\~7.8 | 5.1\~7.1 |
| v3 | 예측 시작점 + 간격 두 배씩 넓혀 구간 잡기 + 보간 | 2.7\~4.5 | 3.8\~4.9 | 4.3\~5.5 |
| v4 | v3 + 첫 측정값과 기울기로 뉴턴식 점프 | 2.4\~3.8 | 3.5\~4.0 | 4.0\~4.8 |
| **v5** | v4 + 정체 판정을 '같은 쪽 두 번 연속'으로 완화 | **2.4\~3.6** | **3.3\~3.9** | **3.7\~4.2** |

### 과정에서 나온 문제
- v2 단위 테스트에서 그냥 비례로 보간하는 버전이 51→39→19→16→14→… 식으로 한 칸씩 기어 내려옴(regula falsi 정체).
  안전장치("절반도 못 줄이면 이분")를 넣었는데 **한 박자 늦게 적용되는 버그**: 다음 위치를 보간으로 정한 뒤에 판단했다. 순서 바꿔 해결.
- v2는 기대보다 효과가 작았다(7.7 → 5\~8). 원인 분석: 가운데(50)에서 시작하는데 정답은 대개 70\~95라 처음 몇 번을 버림 → v3의 동기.
- **허용 오차 실험 기각**: 구간 폭 2\~4에서 멈추면 인코딩은 0.3\~1회 줄지만 손해가 평균 최대 9.4%, 최악 21.8%. 정확히(1)로 고정.
- AVIF는 v3 효과가 작았다(사진마다 최적 품질 차이가 커서 시작점이 자주 빗나감) → v4 동기. v4는 모든 포맷·목표에서 v3보다 낫다.
- 예측표 관찰: 같은 SSIM 0.98이 JPG 품질 96, WebP 91, AVIF 81. SSIM 0.98은 생각보다 엄격하다 → 화면 단계는 0.985/0.97/0.95로.

### 실제 브라우저(Edge 156)
- photo.jpg(768×512, 220KB) '균형(0.97)' → 130KB(-41%), 품질 88.
- **v4를 넣었는데도 5번** → 벤치 평균(3.0)과 안 맞아 추적: 92 통과 → 뉴턴 점프 86 미달 → 보간 87 미달 → **89(이분)** → 88.
  87에서 답은 바로 다음 칸인데, 안전장치가 '구간이 1밖에 안 줄었다'며 이분으로 넘어갔다. 정상 수렴을 정체로 오판.
  → v5: 같은 쪽 끝이 두 번 연속 움직였을 때만 정체로 판정. 이 사진 5→4번, 벤치에서 나빠진 칸 없음, 기어 내려오기 테스트 통과.
- 벤치 평균만 보면 놓쳤을 문제다. 실제 사례 한 건을 끝까지 따라가 본 게 효과가 있었다.
- 한계: SSIM은 밝기만 본다 → 색 번짐(크로마)은 못 잡는다. 고도화 후보.

## 4. 첫 화면 번들
- UI를 붙이자 첫 화면 JS **342KB(gzip 106KB)**. 빈 React(gzip 69KB) 대비 37KB 증가는 화면 코드치고 크다.
- 가설: 공용 패키지에서 형식 판별 함수 하나를 가져오는데, 같은 파일 맨 위의 `import { z } from 'zod'` 때문에 zod 전체가 딸려 옴.
- 수정: 공용 패키지를 `index.ts`(상수·함수)와 `schema.ts`(zod, 서버 전용)로 분리.
- 결과: **254KB(gzip 81KB)**. 가설 맞음. 무거운 WASM(AVIF 3.5MB, HEIC 2MB, SVG 2.5MB, pdf.js 1.3MB)은 전부 따로 쪼개져 해당 기능을 쓸 때만 받는다.

## 5. 실제 브라우저 테스트(Playwright + Edge)에서 잡은 것
13개 시나리오(PNG→JPG 흰 배경, WebP/AVIF, 크기 조절, 스마트 압축, HEIC, PSD 2종, SVG, PDF 합치기/용량/이미지, EUC-KR CSV, 일괄+취소).
매 테스트 끝에 **콘솔 오류 0개**와 **통계에 파일 이름·내용이 없는지**(가로챈 전송 내용 검사)를 확인한다.
- 1차 13개 전부 실패: API 서버가 없어 통계 전송 502 → 테스트에서 가로채 받도록 함. 변환 문제는 아니었다.
- **PSD 실패**: 첫 가설(픽셀 버퍼 크기 불일치)은 **틀렸다.** 실제로는 ag-psd가 `useImageData`여도 내부에서 캔버스를 만들어서, document 없는 워커에서 터짐 → OffscreenCanvas 등록.
  - 이 과정에서 오류가 "파일을 열 수 없어요" 한 줄에 묻혀 원인이 안 보이는 구조 문제를 발견 → 사용자 문구와 원래 원인(detail)을 분리, 원인은 정화 후 관리자 오류 로그로.
- **PDF→이미지 실패**: pdf.js 6에서 캔버스 공장에 `getNoAlphaContext`가 필수가 됨. 소스에서 BaseCanvasFactory 인터페이스를 확인해 맞춤.
- **느슨한 테스트가 틀린 결과를 통과시킴**: 합성본 없는 PSD가 새까맣게 나왔는데 '투명만 아니면 통과'라 통과. 실제 색 검사로 조이자 드러남.
  - 원인: 합성본이 없으면 그 자리가 단색으로 채워진다(실제 포토샵도 비슷). '합성본이 단색인데 레이어엔 내용이 있으면 가짜'로 판단해 레이어를 겹치도록 수정.
  - 그러자 테스트용 '정상 PSD'가 레이어 겹치기로 빠짐 → 원인은 내 테스트 파일(합성본을 한 색으로 만듦, 비현실적). 판단 기준이 아니라 **테스트 파일을 현실적으로** 고침(그라데이션 합성본).
- **PDF 합치기 테스트 오류**: 결과가 객체 스트림 압축이라 텍스트 검색으로 페이지를 못 셈 → pdf-lib로 열어서 셈(테스트 쪽 버그).
- 개인정보 검사의 **거짓 양성**: '010'이 통계에서 발견 → 다시 돌리니 안 나옴. 매번 바뀌는 처리 시간 숫자에 우연히 포함된 것. 문자열 값만 검사하도록 수정.
- pdf-lib는 깨진 PDF도 일단 열어 주고 나중에 TypeError를 냄(단위 테스트로 발견) → 열 때 페이지 수까지 확인.
- 결과: 13/13 통과. 스캔 PDF 1.89MB → 0.46MB(-76%).

## 6. 화면 폭 6종 × 라이트/다크 (자동 검사 + 스크린샷 직접 확인)
자동 검사: 가로 넘침, 모바일 32px 미만 버튼, 파일 이름 칸 폭, 짧은 말이 줄바꿈으로 쪼개지는지.
- 1차: 가로 넘침은 전 폭에서 0건. 모바일 하단 '끄기' 버튼 22×19px → 누르는 영역 36px로.
- **스크린샷을 직접 봐야 보인 것**(자동 검사 통과 상태에서):
  - PC 바로가기 카드 6개가 5+1로 갈라짐(auto-fill) → 3×2 / 2×3 / 1열 고정.
  - 결과 버튼 높이 불일치(52/44px).
  - 320px: 버튼 3개가 폭을 먹어 파일 이름이 'photo.j…'까지만 보이고, '비우기'가 '비우/기'로 쪼개짐.
  - 모바일 '완료!' 알림이 하단 고정 버튼을 가림 → 위로.
  → 보인 문제는 고치는 동시에 **검사 항목으로 추가**(이름 칸 폭, 글자 쪼개짐)해서 다시 생기면 테스트가 잡게 함.
- **검사기의 거짓 양성**: 처음 쪼개짐 검사는 '요소 높이 > 줄 높이×1.6'이라 원래 키 큰 칩·탭이 전부 걸림 → 글자가 실제로 몇 줄에 그려졌는지(Range 사각형) 세는 방식으로 교체.
- **검사기 자체 검증**: 일부러 30px 칸에 '비우기'를 넣어 두 줄로 잡히는지 확인(잡힘). 고치기 전 스타일로 되돌려 이름 칸 검사가 걸리는지도 확인(60px로 걸림).
- 스크린샷 함정: 전체 페이지 이어 붙이기는 고정 헤더가 중간에 끼고, 애니메이션 도중이면 화면이 겹쳐 보인다 → 화면 크기 그대로 + 400ms 대기 후 촬영.
- **미해결 1건**: 전체 e2e 첫 실행에서 25개 중 1개 실패, 이후 3회 연속 + 반복 100회 전부 통과. 어떤 테스트였는지 출력에서 놓쳤다.
  원인 모름. 재발 시 잡으려고 결과를 JSON으로 남기고 재시도 1회(재시도 성공 시 '불안정'으로 표시)를 켰다.

## 7. PWA(오프라인)
설계: 첫 방문에 15MB(AVIF·HEIC·글꼴 등)를 받지 않도록 미리 저장은 앱 껍데기 12개(395KB)만. 기능별 코드·WASM은 처음 쓸 때 저장,
원하면 '오프라인용으로 전부 받기'. 모바일 공유하기(share target), PC 설치 시 파일 열기(file handlers).
- 확인: 오프라인 새로고침에서 화면·격리 헤더 유지, 써 본 기능(WebP) 동작, 안 써 본 기능(AVIF) 실패(정상), 공유하기로 한글 이름 파일 2개 수신.
- **실패**: '전부 받기' 뒤에도 오프라인 AVIF 실패. 원인을 찾기까지 가설이 여러 번 틀렸다.
  1. 가설 '워커 빌드 파일이 목록에서 빠짐' → 목록과 실제 폴더 비교, 153/153 일치. **틀림.**
  2. '캐시에 AVIF가 없다'고 판단 → **잘못 읽음.** 배열이 여러 줄로 찍혔는데 grep이 첫 줄만 보여 줬다. 직접 세어 보니 153개·15.6MB 다 있었다.
  3. 가설 'Vary: Origin 불일치' → 헤더는 실제로 있었지만, `fetch`로 Origin을 달아 꺼내 보는 실험에서 잘 찾아져 **기각.**
  4. 오프라인에서 페이지가 직접 fetch → 200(캐시). 서비스 워커·캐시는 정상. 워커 안 변환만 실패.
  5. 실패한 요청만 찍어 보니 **모듈 스크립트로 불러올 때만** 캐시를 못 찾고 네트워크로 나감.
  → 결론: 3번 가설이 맞았다. **검증 실험이 잘못 설계됐었다.** 크롬은 모듈 스크립트엔 같은 출처여도 Origin을 붙이지만, fetch는 같은 출처 GET에 안 붙인다.
     게다가 '전부 받기'가 기존 항목을 Origin 없이 찾다 못 찾아서, **잘 저장돼 있던 항목을 덮어써 망가뜨리고 있었다.**
  - 수정: 해시 파일은 내용이 안 바뀌므로 캐시 조회·전부 받기 모두 `ignoreVary`. 통과.
  - 배운 것: 가설을 기각하는 실험도 실제 조건(요청 종류)을 재현해야 한다. 그리고 출력은 잘라 보지 말고 센다.
  - 배포 메모: Vite 미리보기 서버가 `Vary: Origin`을 붙인다. 운영 서버(nginx)는 정적 파일에 붙이지 않게.

- 테스트 장치 문제(앱 문제 아님)도 셋: WebKit은 sendBeacon·keepalive 요청과 서비스 워커를 거친 요청을 page.route로 못 가로챔 / Blob 본문을 못 읽음 / 화면 쪽에도 OffscreenCanvas 없음(내 검사 코드가 쓰고 있었다).
- **진짜 UX 버그(아이폰 화면 시험)**: 일괄 변환 중 취소하면 작은 파일은 이미 끝나 있어 '받기'만 남고, 취소된 나머지를 다시 돌릴 방법이 없었다 → '남은 N개 변환' 버튼.

  원인 모르고 '해결'이라 하지 않는다. 테스트를 형식마다 새 페이지로 나누고, 아이폰 실기기 확인 목록에 넣음.

### 기준선 v1 (Edge, 이 PC, 브라우저 프로세스 전체 메모리 최고점을 운영체제에서 0.25초마다 측정)

### 수정
1. **워커 풀 메모리 예산**: 파일 머리(256KB)만 읽어 가로·세로를 알아내고(JPG SOF, PNG IHDR, WebP VP8/VP8L/VP8X, HEIC·AVIF ispe) 예상 메모리 = RGBA × 6(압축은 ×8).
   기기 메모리(deviceMemory, 사파리는 없음 → 모바일 512MB/PC 1.5GB 가정) 기준 예산 안에서만 동시 실행. 혼자서 예산을 넘는 작업은 혼자 돈다. 큰 작업을 마친 워커는 버리고 새로(WASM 힙은 줄지 않는다).
2. **디코딩하면서 줄이기**: 결과가 원본 절반보다 작으면 목표의 2배까지만 펼치고(createImageBitmap resize) 마지막은 Lanczos. 90° 회전 JPEG는 가로·세로를 바꿔 계산(테스트로 고정).
3. **PDF 용량 줄이기 병렬화**: 사진 200장을 한 워커가 차례로 → 하위 워커 풀(최대 4)로 나눔. 하위 워커가 없는 환경은 차례로.
4. **스마트 압축 모자이크 탐색**(아래).
5. 시도마다 인코딩 결과를 Map에 전부 쌓던 것 → 목표 통과한 것 중 가장 작은 하나만.
6. SSIM에서 밝기 배열(5000만 화소면 장당 200MB)을 만들지 않고 줄마다 계산하는 ssimRgba. 기존과 값 1e-6 이내, 속도 동일(500\~517ms).

### 스마트 압축 모자이크 — 가설이 한 번 틀렸다
- v1: 칸마다 **디테일이 가장 많은** 조각을 모아 품질 탐색 → 원본 전체를 그 품질로 1회 인코딩.
  결과: WebP·AVIF가 **원본 SSIM 목표 미달**(0.962, 0.9676), JPG는 필요 이상 높은 품질(+5\~11%). 양쪽으로 빗나감.
  원인: SSIM은 밋밋한 영역의 작은 변화에 민감한데(분산이 작아서), 디테일 조각만 보면 그 부분을 놓친다.
- v2: 디테일 점수 순으로 줄 세워 **밋밋한 곳부터 복잡한 곳까지 고르게(분위수)** 12조각 + 원본 SSIM 확인 후 미달이면 기울기로 올려 재인코딩(최대 2회).
  결과(목표 0.97, Node): **전부 목표 충족**, 용량 손해 0\~5%, 시간 2\~5배 단축. 예) 1200만 화소 AVIF 57초 → 17초, 5000만 화소 JPG 55초 → 11.5초.

## 29. 영상·음성 변환 (F2)

- 처음 계획은 ffmpeg.wasm이었다. GPL 라이선스를 피하려고 브라우저 내장 코덱(WebCodecs)으로 바꿨다. 분리는 mp4box(BSD-3, MP4·MOV·M4A)와 직접 쓴 WebM 읽기(mkv.ts), 묶기는 mp4-muxer·webm-muxer(MIT).
- 다시 인코딩할 필요가 없는 경우(H.264 → MP4 크기 그대로, AAC → M4A·MP4)는 압축된 프레임을 그대로 옮긴다. 화질 손실 0, 시간은 파일 읽기 수준.
- GIF: 인코더는 gifenc(MIT)를 쓰되 색 줄이기(quantize)는 직접 썼다(gifpal.ts, 중앙값 분할). gifenc의 quantize는 PnnQuant.js 포팅인데 원 코드 머리말에 mtPaint(GPL-3) 저작자가 적혀 있고 이식 당시 원본 저장소에 라이선스 파일이 없어 출처가 불분명했다. 묶음본(dist)을 들이면 쓰지 않아도 quantize가 같이 실리므로 원본 모듈(`gifenc/src/index.js`)에서 인코더만 가져온다.
- 한도: GIF는 30초, 프레임 수 × 화소 수 1.5억(넘으면 결과가 수십 MB라 쓸모가 없다).
- 플러그인별 시간 초과: 풀 기본 5분은 큰 영상 재인코딩을 끊었다 → `timeoutMs(inputs)`를 플러그인 계약에 추가, 영상은 5분 + MB당 6초, 최대 30분. 작업 전엔 머리만 읽어 길이를 모르므로 파일 크기로 잡는다.
- 실패 이유를 구체적으로(10개 언어): 코덱 미지원, WebCodecs 없음(Windows용 Playwright WebKit이 그렇다), GIF 길이 초과, 소리를 못 옮겨 빠짐(결과는 주고 경고). 파일 줄에는 분류 한 줄 + 이유 한 줄이 같이 뜬다.
- 시험(e2e/video.spec.ts): 직접 만든 640×360 3초 영상(초마다 배경색 바뀜, 440Hz 소리) MP4·WebM → MP4 480p·WebM·GIF 5fps·M4A. 결과는 우리 코드가 아니라 브라우저 재생기로 열어 길이·크기를 잰다.
  - 통합 때 발견: 그 '재생기로 열기'가 사이트 CSP(`default-src 'self'`, media-src 없음)에 막혀 Edge·Firefox에서 8건 실패했다. 앱은 영상을 재생하지 않으므로 CSP를 넓히지 않고, 시험의 판정을 CSP 없는 빈 탭에서 하게 고쳤다.
  - WebKit(지원 안 함 안내) 시험은 오류 줄이 하나라고 가정해 '이유 한 줄'이 추가되자 strict 모드 위반 → 분류와 이유를 각각 확인하게 고침.

## 32. 보안 점검

점검에서 찾아 고친 것:
- **속도 제한 우회**: `TRUST_PROXY=true`는 손님이 보낸 X-Forwarded-For의 맨 왼쪽 값을 믿어, 머리글만 바꾸면 로그인 5회/분 제한이 풀렸다 → 겹수(`TRUST_PROXY_HOPS`, 기본 1)만큼 오른쪽에서만 믿는다. Fastify가 숫자 설정을 막아 두어 함수로 준다.
- **SSR 캐시 오염**: 캐시 키가 디코드된 `$uri`라 `/es/avif%2Dto-png`(SSR엔 없는 주소 → 404)가 `/es/avif-to-png` 자리에 캐시됐다 → 키를 SSR이 실제로 받는 원문 주소(쿼리 제외)로.
- **역슬래시**: nginx는 `\`를 글자로 보지만 SSR(WHATWG URL)·브라우저는 `/`로 바꾼다. `/a/..\__ssr/metrics`가 내부 경로에 닿았고, 상대 이동 주소 `/\evil.com`은 다른 사이트로 갔다 → `\`가 든 주소는 404.
- **절대 주소 이동**: nginx가 이동 주소에 자신의 `http`·`8080`·Host를 박아, HTTPS 앞단 뒤에서 `http://도메인:8080/…`으로 보냈다 → `absolute_redirect off`.
- API 응답에도 nosniff 등 보안 머리글(같은 snippet).

- 관리자 '알림' 탭: 아래 고정 저장 막대(70px)가 맨 아래 규칙의 스위치를 덮어, 시험의 클릭이 막대에 떨어졌다(elementFromPoint로 확인: 스위치 중심 y=688, 막대 650\~720). 키보드 초점도 같은 이유로 가려진다(2.4.11) → 막대가 있을 때 문서에 `scroll-padding-bottom: 80px`. 스크롤·초점 이동이 막대 위에서 멈춘다.
- 남은 것: 스크롤 키프레임의 opacity 시작값(연출 중 흐린 글자), 영상 형식 꼬리표 전용 색(지금은 회색 '기타').

## 38. 리눅스 CI에서 처음 드러난 것 (2026-11-05)

- 첫 공개 푸시로 GitHub Actions(ubuntu)를 처음 돌렸다. 지금까지 시험은 전부 윈도우였다.
- **리눅스 파이어폭스 H.264 avcC 버그**: WebM(VP9) → MP4가 640×360이 아니라 16×160으로 열렸다(3회 연속). Playwright 리눅스 이미지로 재현한 뒤 인코더가 주는 avcC를 그대로 찍어 보니, SPS·PPS 앞에 NAL 머리 바이트가 한 번 더 들어 있었다(`67 67 64 00 1e …`, 길이 25 — 영상 안의 SPS는 `67 64 00 1e …` 24바이트). 재생기가 깨진 SPS로 크기를 계산한 것. MP4 → MP4는 다시 인코딩하지 않아 이 경로를 안 탔다.
  → `ops/avcc.ts` `repairAvcC`: avcC의 SPS·PPS가 첫 키프레임 안의 것과 다를 때만 그것으로 다시 만든다(크롬·윈도우처럼 맞으면 그대로). 실제로 받은 바이트로 단위 시험 4개, 리눅스 파이어폭스·웹킷 영상 시험 10개·윈도우 11개 통과.
- CI 설정 문제 둘: compose가 요구하는 `GRAFANA_ADMIN_PASSWORD`를 시험용 .env에 안 넣었다 / 알림 시험의 웹훅 `host.docker.internal`이 리눅스 Docker엔 없다(`extra_hosts: host-gateway`) / API 멈춤·재시작 시험이 `--env-file` 없이 compose를 불렀다.
- 시각 회귀 기준 화면은 윈도우 글꼴 렌더 기준이라 리눅스에선 건너뛴다.
